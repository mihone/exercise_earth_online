# 工作流规则 - 操作规范

本规则约束 Claude 自身的工作流程，非业务代码规则。目标是减少反复踩同类坑。

---

## ⚠️ 1. 失败超过 2-3 次必须停止并向用户汇报（最高优先级）

**这是所有工作流规则里最重要的一条，没有例外。**

- 任何操作（编译、命令执行、文件查找、工具调用等）**失败 2 次后，第 3 次必须是最后一次尝试**。
- 第 3 次仍失败：**立即停止一切重试**，向用户汇报：
  1. 尝试了哪些方法
  2. 每次失败的关键原因（错误日志摘要）
  3. 自己的推测或需要用户提供什么信息
- **严禁**在失败后只换个参数继续盲目重试，不向用户报告就继续撞墙。

**为什么**：用户知道环境细节（路径、配置、版本），盲目重试不仅浪费时间，还会让用户以为进展正常——这比直接报错更糟糕。曾经 Maven 编译找不到模块，连续尝试了四种写法都失败，始终不汇报，直到用户发现才停下。

**如何应用**：
- 第 1 次失败 → 换思路再试一次
- 第 2 次失败 → 最后一次尝试，同时在心里准备好失败报告
- 第 3 次失败 → 停下来，直接告诉用户："我试了 X、Y、Z 都失败了，原因是 [摘要]，需要你帮确认 [具体问题]"

## 2. 查找依赖 / jar 包 / 工具路径前，先查 MEMORY.md

- 遇到"找本地 Maven 仓库""找某个 jar""找某个外部工具路径"这类场景，**第一步**永远是读 `~/.claude/memory/MEMORY.md`，看看是否已有 reference 类型的记忆。
- **严禁**直接 `find /` 或 `mdfind` 全盘扫描——代价高、常常找不到、会打断用户。
- 记忆里没有时，按下列顺序尝试：
  1. 询问用户（最保险）
  2. 约定俗成的位置（如 `~/.m2/repository`）
  3. 最后才考虑全盘搜索

**为什么**：曾经为了找 `daas-client-soa.jar` 在 `~/.m2` 和全盘 `find` 上浪费大量时间，其实用户本地仓库在 `/Users/xuxinyu/repository`，这类路径是稳定的、应该记忆化。

**如何应用**：在任何 Bash 调用涉及 jar / 依赖 / 仓库 路径查找之前，先 Read MEMORY.md。

## 3. Maven 增量编译：`Nothing to compile` 不是错误

- `mvn compile` 输出 `Nothing to compile - all classes are up to date` 属于**增量编译器的正常行为**，不代表失败，也不代表新文件没被编进去。
- 验证编译产物是否存在，**不要**重跑 mvn：直接 `ls target/classes/<包路径>/` 看新 class 文件是否生成、时间戳是否更新。
- 只有真的看不到预期 class 文件时，才用 `mvn clean compile` 或 `touch` 源文件强制重编。

**为什么**：上一次看到 "Nothing to compile" 误以为 maven 有问题，白跑了 40s 第二轮编译。

**如何应用**：写完 Java 新文件后走以下流程：
1. `mvn -pl <module> -am compile -DskipTests`
2. `ls -la <module>/target/classes/<package_path>/` 验证 .class 存在且时间戳新
3. 看到 "Nothing to compile" 不惊慌，走第 2 步确认即可

## ⚠️ 4. 写完代码必须按 code-rule 自查再提交

每次写完或修改任何 Java 代码后，在输出给用户之前，必须对**实际新写或修改的代码**逐条对照 `code-rule.md` 自查一遍，全部符合才输出。

未修改的老代码、仅换行/格式调整的行、抽象方法声明，不在自查范围内。

**自查范围不只是 code-rule**：本次改动若涉及业务状态/成对动作（成团/不成团、上线/下线、开/关、加/删、启用/停用等），还要额外对照 `biz-rule.md` 第 5 条「成对状态动作必须闭环」自查一遍——确认「正向写状态」和「反向清状态」在所有条件组合下是对称的，清理/回滚逻辑没有因为被埋进某个前置分支而够不着。这是每次写完代码的固定自查环节，不是只有 review 时才做。

## ⚠️ 5. 测试失败时不得擅自修改生产代码（多次违反）

- 任务是写/改单元测试时，测试失败的第一反应是**报告给用户**，让用户判断是测试写错了还是生产代码有 bug。
- **严禁**在没有用户明确指示的情况下，因为测试跑不过就去改生产代码——即使看起来像 bug。
- 修改生产代码是另一个任务，必须单独确认。

**为什么**：多次在改单元测试途中发现测试报错，自行判断为"生产代码 bug"并动手修改，结果用户一句话就指出了正确方向（如"不用 MappingUtils，直接手动 merge"），之前的改动全部作废，浪费了多轮编译时间。

**如何应用**：
- 测试失败 → 先检查是否是测试本身写错了（mock 配置、期望值、`throws` 声明等）
- 如果确实像生产代码问题 → 停下来告诉用户："测试在 X 处抛了 Y 异常，可能是生产代码的问题，要我修吗？"
- 等用户确认后再动生产代码

---

- 一次 Explore 调用**只问一个主题**，prompt 控制在 200 字以内。
- 多个独立主题应该**并发**多个 Explore agent（同一条消息里发多个 tool call），而不是一个 prompt 塞 5 个子问题。
- Agent prompt 要求具体产出（"用 file:line 格式""不超过 300 字"），否则容易拿到啰嗦的大段文字。

**为什么**：一次塞 5 个子问题的 prompt 虽然省一轮调用，但 agent 返回的报告冗长、重点分散，阅读和提取信息反而更慢。并且长 prompt 也让 agent 容易发散，质量下降。

**如何应用**：
- 单主题 Explore：prompt 聚焦，要求 file:line 简短回答
- 多主题：拆成多个 Explore，parallel 调用
- 不要把"探索代码"和"设计方案"混在同一个 Explore prompt 里 —— 后者应由 Plan agent 处理
