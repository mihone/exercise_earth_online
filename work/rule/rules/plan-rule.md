# Plan 模式规则 - Prompt 归档

约束 Claude 在 plan 模式下的行为，目标是让 plan 文件自带"产生它的 prompt 历史"，方便后续排查"当时为什么这么定"。

## 1. 首次写 plan 必须携带 Prompt 历史段

- 在 plan 文件末尾固定维护一个 `## Prompt 历史` 段落。
- 首次写入 plan 时，必须把**当前触发 plan 的 user prompt 原文**作为第 1 条记录进去，不要改写、不要总结、不要裁剪。
- 如果在正式生成 plan 之前，用户已经在同一 plan 模式内连续补充了多条需求（例如先"做 X"、又说"再加 Y"、再说"Y 改成 Z"），应把这几条按时间顺序全部记录，每条单独一条。
- 聊过但与本 plan 明显无关的上下文（plan 之前的闲聊、不相关的前置操作）不记录。

**为什么**：plan 落盘后执行过程中常常出现分歧，回头查"这条 plan 到底是根据哪句话定的"会比翻 transcript 快得多。压缩总结会丢失关键措辞，因此必须原文留存。

**如何应用**：调用 `ExitPlanMode` 前，plan 文件末尾必须已经有 `## Prompt 历史` 段并至少含 1 条记录。没写就不要退出 plan 模式。

## 2. 每次修改 plan 前必须先 append 触发 prompt

- 用户后续让你修改 plan（增删需求、改方案、调整范围）时：**先把触发本次修改的 user prompt 追加到 `## Prompt 历史` 末尾**，再动 plan 正文。
- 追加和修改在同一次 Edit 里完成也可以，顺序不强制，但两者必须一起落盘，不允许"只改正文、不记 prompt"。
- 对 plan 的修改无论大小都要记，包括只改一句措辞，因为后续排查并不知道当时的"小改"实际影响了什么。

**为什么**：plan 批准后还会反复迭代，只留"首次 prompt"等于丢失了 80% 的决策信息。只有把每次修改的触发语都留下来，历史才完整。

**如何应用**：收到"把 X 改成 Y""再加一条 Z""这步去掉"这类针对现有 plan 的指令时，动手前先打开 plan 文件 append prompt。

## 3. Prompt 历史段的格式

统一用如下格式，避免每次风格漂移：

```markdown
## Prompt 历史

> 本段由 plan-rule.md 规则维护，记录生成与修改 plan 的原始 user prompt，请勿改写。

### #1 初始需求
{{原始 prompt 原文}}

### #2 修改 - {{一句话概括意图，例如"补充时区降级策略"}}
{{原始 prompt 原文}}

### #3 修改 - {{...}}
{{原始 prompt 原文}}
```

- 序号从 1 开始，单调递增。
- 标题用"初始需求"或"修改 - {{意图}}"；意图一句话，便于 TOC 里扫读。
- 正文是 prompt 原文，多行 prompt 保留换行，不用引用块包裹（引用块会吞换行语义）。

## 4. 不要把 Prompt 历史段当成设计文档

- `## Prompt 历史` 是**审计记录**，不是 plan 正文的一部分，不要在这里补充分析、结论、TODO。
- 读 plan 执行任务时，以 plan 正文为准；`## Prompt 历史` 只在排查分歧或回看动机时使用。
- 如果 prompt 历史里的某条已经不再适用（需求被推翻），**不要删**——在正文对应位置说明即可。历史需要保留时间线。

## 5. 非 plan 模式不适用

- 本规则只在 Claude Code 的 plan 模式下生效（即涉及 `EnterPlanMode` / `ExitPlanMode` 的工作流）。
- 普通对话里零散的 prompt 不需要归档，避免污染其他文件。

## 6. plan 末尾必须有 code-rule 自查步骤

每个 plan 正文末尾必须有一条独立步骤：写完代码后对照 `~/.claude/rules/code-rule.md` 逐条 review 本次改动，违规处当场改掉，改完再查一遍直到全部符合。

`ExitPlanMode` 前没写就补上再退出。

## 7. plan 末尾必须有「状态闭环」自查步骤

如果 plan 的方案涉及成对状态动作（成团/不成团、上线/下线、开/关、加/删、启用/停用等），plan 正文末尾必须有一条独立步骤：写完代码后对照 `biz-rule.md` 第 5 条「成对状态动作必须闭环」，逐格确认「正向写状态」和「反向清状态」在所有条件组合下对称，清理/回滚逻辑没有被埋进某个前置分支而够不着。

写完这条自查后，还要**回头 review plan 本身的逻辑**：方案里有没有「某一步只写了正向、没设计反向」「某个清理动作依赖的前置条件比它实际用到的入参更严」这类不闭环的地方。有缺口就直接在 plan 里补全；拿不准是否闭环的，不要自己拍板，按 `biz-rule.md` 第 4 条列 TODO 或直接和用户讨论。

`ExitPlanMode` 前没写就补上再退出。方案不涉及成对状态动作时，本条可空转跳过。

## 8. plan 执行完代码后必须有 review-rule 自查步骤

每个 plan 正文末尾，在规则 6（code-rule 自查）和规则 7（状态闭环自查，如适用）之外，必须再有一条独立步骤：写完代码后，对照 `~/.claude/rules/review-rule.md` 第 3 节完整过一遍高频对齐场景清单（摘录 + 并排对齐 + 真值表，含 3.6 代码健壮性检查），命中的矛盾点当场修复，改完再查一遍直到全部符合。

**为什么**：code-rule.md 自查抓的是"单点写法是否规范"，抓不住"多处代码拼起来才矛盾"的隐蔽 bug——比如两个结构几乎一样的姊妹方法，一个对中间集合结果判空提前 return，另一个没判空直接传给拼 SQL `IN` 条件的 DAO 方法，导致空集合场景下 SQL 语法报错上线。这类问题顺序读代码看不出来，必须靠 review-rule.md 的"跨点对齐"方法才能抓到，且必须在 plan 收尾这个动作里主动跑一遍，不能等上线报错后才补。

**如何应用**：`ExitPlanMode` 前该步骤必须已经写进 plan 正文；实际写完代码后，必须真的按 review-rule.md 走一遍并修复发现的问题，不能只是形式上留了这句话却没执行。
