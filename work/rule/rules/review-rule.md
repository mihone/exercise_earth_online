# Code Review 规则 - 常规体系之外的额外检查项

本规则用于 **review 阶段**（自查 diff、正式 code review、requesting-code-review skill、`/code-review` skill、review PR），不是写代码阶段。

**定位**：这些是常规 review 体系（跑测试、看编码规范、逐行读逻辑）**之外的额外检查项**。常规 review 会做的事情继续做；本规则里列的场景，是需要在常规体系之上**额外**跑一遍的清单。

**目标**：抓那种顺序读代码几乎抓不到的隐蔽 bug —— 通常是"每处单独看都对，合起来读才矛盾"这一类，必须靠"结构化对齐"和"跨点视角"才能暴露。

---

## 1. 触发条件

**只要在做 code review，就必须额外考虑本规则里的所有检查项。**

无论改动大小、涉及的是新增还是修改、涉及的是业务代码还是基础设施，只要进入 review 视角（自查 diff、看别人的 PR、跑 /code-review），常规 review 体系之外，都要再过一遍本规则的检查项清单（下方第 3 节）。

不要以"改动小""看起来无关""应该没问题"为由跳过 —— 这类隐蔽 bug 的特征就是每处看都合理。跳过的唯一理由是"本条检查项**明确不适用**"（例如改动完全不涉及条件判断/状态字段，那"阈值一致性"这一项就空转跳过，但其他项仍然要过）。

---

## 2. 通用动作：摘录 + 并排对齐

不要顺序读代码，改用如下动作：

1. **摘出所有引用点**：把涉及同一字段/概念的代码行连同 file:line 摘到同一处，形如
   ```
   Validator.java:71   if ("true".equals(logSwitch) && config.getRate() <= 100)
   Validator.java:90   if (rate >= 100) { return true; }
   ```
2. **代入临界值跑真值表**：对每个临界值（0、1、边界最大最小、null、空串）逐个代入所有引用点，检查语义是否自洽
3. **发现矛盾就停下**：出现"两处语义打架""某个值同时命中两个互斥分支""某个值哪个分支都不命中"，都要 flag，不要自己脑补"应该是没问题吧"

---

## 3. 高频对齐场景（本清单会持续追加）

> 每加一类新场景，直接往下追加小节；触发方式已在第 1 节收敛为"只要 review 就跑"，不用再在这里写触发条件。

### 3.1 同一阈值的比较运算符是否一致
把所有把该字段当阈值用的比较（`>=`、`<`、`==`）摘出来，在临界点（如 100、0）代入检查语义是否互斥/互补。

**典型陷阱**：一处 `rate >= 100` 视为全量，另一处 `rate <= 100` 视为需要记日志 —— rate=100 时两个语义同时成立，逻辑打架。

### 3.2 同一字段的"写入值域" vs "读取判断"
上游能写入哪些值，下游 `if / switch / equals` 是否覆盖所有值。特别是：
- 新增枚举值后，是否所有读取点都处理
- 上游可能写入 null，下游是否所有分支都判 null

### 3.3 成对判断是否真互补
对成对方法/条件（`isValid` vs `isInvalid`、`shouldLog` vs `shouldSkip`），画一遍真值表，看是否存在"两边都 true"或"两边都 false"的洞。

### 3.4 特殊值的跨点语义
同一特殊值（null、`""`、0、-1）在链路多环节被解读的业务含义是否一致。比如上游把 null 当"无过滤"，下游把 null 当"过滤全部"，就是链路语义漂移。

### 3.5 成对状态动作的闭环（写入点与清理点是否镜像）
对成对动作（成团/不成团、上线/下线、开/关、加/删），确认：**正向动作能在哪些条件组合下落下状态，反向动作是否能在同一条件组合下反向清掉**。

具体做法：
1. 摘出"正向写状态"的**所有**入口（含带 `if` 前置条件的），和"反向清状态"的**所有**入口。
2. 画条件矩阵（如 有团/无团 × 成团/不成团），逐格确认是否都有对应动作，找"空格子"。
3. 重点检查：**清理/回滚逻辑是否被放在了"只有某个前置条件成立才进得了"的分支里**，而它实际只用到了入参的子集（例如只依赖 `productId + departureDate`、用不到 `tourId`）——这种情况必须下沉成独立方法，让所有分支都能调。

**典型陷阱**：成团在"无团"时也写 `group_status`，但不成团的删除逻辑藏在 `handleFailedNotice`（仅"有团"分支可进），导致"无团 + 不成团"删不掉。

### 3.6 代码健壮性检查（NPE、空值、类型转换异常等，需结合上下文判断）

不局限于某个固定场景（如批量查询/更新），而是对本次改动里**所有**"可能失败的取值/调用点"过一遍：外部接口返回值、DAO 查询结果、集合类中间结果（filter/convert 之后）、类型转换（拆箱、强转、`Long.parseLong` 等）、链式取值。对每一个这类点，回答两个问题：

1. **这个值在当前业务上下文里，真的可能是 null / 空集合 / 转换失败吗？** 不能只看方法签名判断"可能为 null 就算它有风险"，要结合上游调用链、业务场景判断"是否真的会走到这个值"。判断不了就按 `biz-rule.md` 第 4 条列 TODO，不要自己拍板"应该不会"。
2. **如果真的发生，当前代码是显式处理了，还是裸用**（直接 `.getXxx()`、直接传给下一层、假设下游会兜底）？

**典型陷阱**：`platformIds` 是过滤后的中间结果（`e.getInternalOrderId() != null`），可能为空集合；调用方没有判空就直接传给 `tourInfoExtDao.getTourOrderByOrderId(platformIds)`，该 DAO 方法在 SQL 层拼 `IN` 条件，空集合导致拼出非法 SQL 报错。而结构几乎相同的姊妹方法对同类中间结果 `erpOrderIds` 有 `if (CollectionUtils.isEmpty(erpOrderIds)) { return; }` 判空——两个姊妹方法本该对称却不对称，正是本节要抓的模式。

**辅助技巧**：库里若有结构相似的姊妹方法（处理逻辑高度重复、参数语义类似），并排对比两者在"取到中间结果后是否判空""如何兜底"上是否一致，不一致大概率是漏洞而非有意设计。

---

## 4. 输出方式

自查发现矛盾时：
- 如果是自己的 diff：直接修，修完再跑一次本规则确认
- 如果是别人的 PR：以 file:line 精确指出两处矛盾点，用真值表说明为什么冲突，不要只写"这里边界处理有问题"这种模糊表述

拿不准是否真的矛盾（比如可能有业务语义兜底），按 `biz-rule.md` 第 4 条列 TODO 交给用户判断，不要自己拍板"应该没问题"。

---

## 5. 何时可以只跳过某一小节

不整体跳过本规则，但**单个小节**如果改动明确与之无关，可以空转跳过。判断标准：

- 3.1（阈值比较）：diff 里没有任何数值/阈值比较 → 跳过
- 3.2（写入值域 vs 读取分支）：diff 里没有新增枚举/字段值域，也没有新增读取分支 → 跳过
- 3.3（成对判断互补）：diff 里没有成对的正反判断方法/条件 → 跳过
- 3.4（特殊值跨点语义）：diff 里没有涉及 null / 空串 / 0 / -1 等特殊值的判断 → 跳过
- 3.5（成对状态动作闭环）：diff 里没有成对的状态写入/清理动作（成团/不成团、上线/下线等）→ 跳过
- 3.6（代码健壮性检查）：几乎总是适用，仅当改动完全不涉及任何外部调用结果、集合中间结果、类型转换的使用（如纯常量/纯配置改动）→ 跳过

拿不准是否适用时，宁可过一遍，不要跳。代价要认：本规则会让 review 变慢，因为需要跳出"顺序读"，主动做跨点摘录和真值表。改动越大、跨点越多，收益越明显；改动很小则大部分小节空转，成本可控。
